# PyBaMM W10 正式运行就绪整改设计

## 1. 目标

在不改变 `2026-08-17-pybamm-w10-3c-aging-design.md` 物理模型、实验边界和两种 RPT 模式定义的前提下，补齐现有实现的状态恢复、UDDS 周期识别、运行证据、输出字段、失败分类和真实 PyBaMM 短求解验证，使代码达到可启动正式 350-cycle 运行的工程条件。

整改完成阶段只执行受控的短 smoke test，不启动 350-cycle 正式仿真。

## 2. 验收边界

正式运行就绪必须同时满足：

- 指定解释器为 `C:/Users/Lenovo/anaconda3/envs/battery/python.exe`，运行前拒绝其他解释器。
- PyBaMM、NumPy、CasADi、求解器及操作系统版本写入环境元数据。
- W10 Step 14 的重复周期由数据识别并验证，不由未验证的常量替代。
- 主 DFN 使用显式的约20% SOC规范初态，初始化方法、状态向量哈希和相关指纹可追溯，不依赖PyBaMM默认初态。
- virtual RPT 有可核验的非侵入性证据。
- strict-W10 特殊循环、cycle-350 终止规则和 `Q_ref` 更新顺序与原设计一致。
- checkpoint 可以恢复，且恢复结果与连续运行在规定容差内一致。
- 从任一 checkpoint 恢复时，checkpoint 之后产生但未被该 checkpoint 提交的输出可以自动、可审计地回滚。
- 输出文件和字段覆盖原设计要求。
- 物理失败、数值失败和成功状态互斥且可追溯。
- 纯逻辑测试、文件集成测试和受控真实求解 smoke test 全部通过。

## 3. UDDS 最小重复单元识别

### 3.1 已确认的数据事实

对 `W10-1.mat` 的 Step 14 做只读分析得到：

- 共有 25 个连续 Step-14 数据段。
- 每段持续约 18833.7 至 18834.5 s。
- 每段包含 7 个完整的 2600 s 单元及一个尾部不完整单元。
- 25 个数据段在 2400 至 2800 s 候选范围内的最佳周期均为 2600 s。
- 2600 s 移位相关系数范围为 0.9996889 至 0.9996927。
- 2600 s 移位归一化 RMSE 范围为 0.02210 至 0.02223。
- 1300、650、520、325、260 s 等主要约数不具有完整波形重复性。

因此，2600 s 是 W10 Step 14 在协议意义上的最小完整重复单元。它不是指连续采样中不存在更短的局部相似脉冲，而是指能够完整复现本工况电流结构、回馈段和净容量特征的最小周期。

### 3.2 正式实现

UDDS 提取器必须：

1. 按时间间隙把全部 Step-14 样本拆分为连续段。
2. 在配置的合理候选范围内对每个连续段搜索周期。
3. 要求各有效段对同一周期达成一致，并保存候选评分、相关系数、归一化误差及约数排除证据。
4. 从全部有效段提取所有完整单元；对 W10-1 预期获得 175 个完整单元。
5. 把各单元重采样到共同的 1 Hz 相位网格后求平均。
6. 按单个2600 s单元比较原始与平均波形的净 Ah、回馈 Ah、RMS、最小值和最大值，避免把多个单元总量与单个平均单元直接比较。
7. 对最后一个截断采样段使用分段线性电流积分的解析根，生成满足目标净 Ah 的精确终点。
8. 验证单次 UDDS 剩余目标和 Step 5–6 累计80%目标的相对误差均不超过0.1%。

基础波形验证写入 `udds_validation.json`，逐循环目标验证写入 `udds_cycle_validation.jsonl` 和 `run.log`。

## 4. 状态机与诊断

### 4.1 主 DFN 规范初态

主 DFN 的初始状态显式固定为约20% SOC。配置必须包含 `initial_soc = 0.20`，生产 backend 在任何首次求解前通过固定且版本可记录的 PyBaMM 初始化路径构造一次规范初态，不得依赖 `Simulation.solve` 的隐式默认初态。

初始化记录至少包括：

- `initial_soc` 配置值
- PyBaMM 初始化方法及相关调用参数
- 参数集、参数覆盖、模型选项和网格指纹
- 初始化后的完整状态向量哈希
- 初始化后的主时间、日历时间、放电容量计数器及关键化学计量比
- Python、PyBaMM和求解器版本

virtual 模式的 cycle-0 RPT 必须从该规范初态创建隔离诊断分支。RPT 完成并丢弃分支后，主 DFN 的状态向量哈希、主时间、日历时间、容量计数器和协议阶段必须与诊断前的规范初态完全一致。strict-W10 同样从该规范初态开始，但允许 cycle-0 RPT 按设计推进主状态。

checkpoint 为 cycle 0 时也必须保存并验证规范初态指纹。恢复时若当前模型重建得到的规范初态指纹与运行记录不一致，拒绝恢复。

### 4.2 协议阶段

使用显式协议阶段枚举：

- `INITIAL_RPT`
- `STANDARD_CHARGE`
- `RPT_PRECONDITIONING`
- `RPT_CAPACITY_DISCHARGE`
- `POST_RPT_RECOVERY`
- `STEP5_C4_DISCHARGE`
- `STEP6_UDDS`
- `CYCLE_COMPLETED`
- `RUN_COMPLETED`

循环编号只有在 `STEP6_UDDS` 成功达到累计80%目标后才增加。checkpoint 记录协议阶段，使恢复逻辑可以拒绝模糊或不完整状态。

### 4.3 virtual RPT

virtual RPT 使用独立诊断 backend 或与主 backend 隔离的诊断分支，不能把诊断解临时写成主 backend 的当前解。

诊断前记录：

- 主状态向量哈希
- 主状态时间
- 主日历时间
- aging-cycle 编号
- 主协议阶段

诊断分支在丢弃前记录诊断开始时间、诊断结束时间、诊断耗时、`q_rpt_start`、`q_rpt_end` 和容量。随后再次核对主状态的上述字段。任何主状态变化均属于实现错误，并归为 `NUMERICAL_FAILURE`。

允许保留的唯一诊断控制结果是成功且有限、为正的 `Q_ref`。

### 4.4 strict-W10

strict-W10 RPT 直接推进主状态，但不增加 aging-cycle 编号。节点小于350时，RPT 后的1C CC-CV和1 h静置属于下一特殊循环的充电阶段。特殊循环只在完成 Step 5 和 UDDS 后增加一次编号。cycle-350 RPT 后不执行恢复充电。

HPPC 和 EIS 继续通过稳定接口抛出 `NotImplementedError`，不得静默跳过。

## 5. 容量目标与事件

每批循环冻结最近一次成功 RPT 的 `Q_ref`。Step 5 开始时只记录一次 `q_window_start`：

- Step 5 事件：`Discharge capacity - q_window_start = 0.20 * Q_ref`
- UDDS 事件：`Discharge capacity - q_window_start = 0.80 * Q_ref`
- UDDS 剩余目标：`0.80 * Q_ref - Delta_Q_5,actual`

Step 5 结束后验证20%目标；UDDS 结束后分别验证UDDS剩余目标和累计80%目标。2.5 V先于容量事件触发时归为 `PHYSICAL_PROTOCOL_FAILURE`。

每个协议阶段声明预期终止事件。合法但不符合当前阶段预期的 PyBaMM 物理事件属于物理协议失败；求解器异常、表达式错误、NaN/Inf和非法状态属于数值失败。不得仅依靠模糊字符串包含判断完成分类。

## 6. Checkpoint 与恢复

### 6.1 Checkpoint 内容

checkpoint 至少保存：

- 可恢复的完整 PyBaMM `last_state`
- 状态向量哈希
- aging-cycle 编号
- 主时间和日历时间
- RPT 模式和协议阶段
- 最近成功的 `Q_ref` 及来源节点
- 当前批次20%目标、80%目标和当前 UDDS 剩余目标
- 配置指纹、原始 W10 文件指纹及生成后 UDDS 指纹
- Python、PyBaMM和求解器版本
- 输出事务号及各汇总文件的最后已提交行

### 6.2 写入顺序

RPT 成功后必须按以下顺序处理：

1. 验证容量有限且为正。
2. 写入 RPT 事务。
3. 若节点小于350，更新 `Q_ref`、来源节点和下一批目标。
4. 原子写入包含新 `Q_ref` 的 checkpoint。

checkpoint 先写临时文件、完成同步后原子替换正式文件，防止半写状态。

### 6.3 恢复入口

CLI 增加 `--resume <checkpoint>`。恢复时必须核验配置、模式、输入文件、UDDS、Python/PyBaMM/求解器版本及输出事务。如果不匹配则拒绝恢复，不创建拼接结果。

恢复一致性语义统一定义为：

- checkpoint 提交边界以内的数据是已经承诺的运行历史。该边界内任一文件前缀、行数、哈希、事务号或独立文件与提交清单不一致时，必须拒绝恢复并归为 `NUMERICAL_FAILURE`。
- checkpoint 提交边界之后的数据不是已经承诺的运行历史。边界后新增的 CSV/JSONL/日志尾部、时序、图形、临时 checkpoint 和其他派生文件不得导致恢复被拒绝；它们必须先按6.4节自动回滚，再继续正常恢复。
- 不得把“边界后的合法未提交尾部”误报为已提交数据损坏，也不得把“边界内损坏”当成可清理尾部。

恢复测试必须比较连续运行与“运行—保存—加载—继续”两条路径的最终状态向量、时间、容量计数器、循环编号和关键退化变量。

### 6.4 Checkpoint 后未提交输出的自动回滚

此项是开始正式编码前的强制要求，不得降级为人工清理说明。

每个 checkpoint 必须包含一个输出提交清单，至少记录：

- 已提交的全局事务号
- 每个追加型文件的已提交字节偏移、数据行数和已提交前缀哈希
- 已提交的时序、图形和其他独立文件的相对路径、大小及内容哈希
- 与该事务匹配的最后完成循环和最后完成 RPT 节点

输出事务采用“先写输出、完成同步，再原子写 checkpoint”的顺序。若进程在输出写入后、checkpoint 提交前中断，这部分输出属于 checkpoint 之后的未提交尾部。

从 checkpoint 恢复时，运行器必须在继续求解前执行回滚：

1. 对照 checkpoint 清单验证所有已提交文件前缀的大小、行数和哈希。
2. 如果已提交前缀被修改、缺失或损坏，拒绝自动续跑并归为 `NUMERICAL_FAILURE`，不得用截断掩盖已提交数据损坏。
3. 将追加型 CSV、JSONL 和日志截断到 checkpoint 记录的已提交字节偏移。
4. 将 checkpoint 清单之外或事务号更大的时序、图形、临时 checkpoint 和其他派生文件移动到本次运行目录下的 `rollback/<resume-timestamp>/`，保留审计副本，不直接永久删除。
5. 图形视为可再生派生输出；从旧 checkpoint 恢复时，移动所有依赖未提交数据的图形，并在运行重新完成后生成。
6. 原子更新输出清单，记录回滚来源 checkpoint、回滚文件、截断字节数、原事务号和恢复事务号。
7. 只有回滚及清单写入全部成功后，才允许加载状态并继续求解。

回滚操作必须在6.5节定义的全生命周期单写者锁内进行。回滚失败、已提交前缀校验失败或清单无法原子写入均归为 `NUMERICAL_FAILURE`。

故障注入测试至少覆盖：

- CSV 行已写入但 checkpoint 尚未更新
- JSONL 已追加但 checkpoint 尚未更新
- RPT 或代表循环时序文件已完成但未提交
- 图形已生成但未提交
- 输出前缀被人工篡改
- 回滚过程中再次中断，并在下次恢复时幂等地完成回滚

验收要求是：恢复后所有活动输出均与选定 checkpoint 的提交清单完全一致；未提交尾部已从活动输出移除且可在 `rollback/` 中审计；随后继续运行不得产生重复循环行、重复 RPT 行或事务号倒退。

### 6.5 运行目录全生命周期单写者锁

每个 `--run` 或 `--resume` 进程在读取、验证或修改运行目录前必须获取该目录的排他单写者锁，并一直持有到以下任一条件发生：

- 成功写出最终 `COMPLETED` 状态并关闭所有输出
- 成功写出 `PHYSICAL_PROTOCOL_FAILURE` 或 `NUMERICAL_FAILURE` 状态及最后有效checkpoint并关闭所有输出
- 进程异常退出，操作系统自动释放锁句柄

锁必须覆盖 preflight、输出目录初始化、checkpoint验证、自动回滚、状态加载、求解、输出事务、checkpoint写入、图形生成和最终状态写入整个生命周期，不能只覆盖回滚阶段。

锁实现必须使用操作系统级排他文件锁或提供等价的进程退出自动释放语义，不能只依赖可能遗留的普通标记文件。锁元数据记录运行目录、PID、主机、启动时间、命令模式、配置指纹和所选checkpoint。第二个进程无法获取锁时必须在读取或写入活动输出前立即退出，并明确报告目录已被占用；不得把锁竞争本身写入被占用的运行目录。

锁文件中存在旧元数据但操作系统锁已释放时，新的进程可以获取锁，并把旧锁元数据作为异常退出审计信息记录到新的恢复事务。不得通过猜测PID或直接删除锁文件绕过仍有效的操作系统锁。

并发测试至少启动两个独立进程竞争同一运行目录，验证只有一个进程能够进入 preflight 或恢复流程，另一个进程不会改变checkpoint、事务号、CSV、JSONL、日志、时序或图形。

## 7. 输出与内存

### 7.1 循环汇总

`cycle_summary.csv` 补齐：

- 循环、模式、起止时间和各阶段持续时间
- `Q_ref`、来源节点及三个容量目标
- Step 5实际值、UDDS实际值和累计窗口实际值
- 充电 Ah、放电 Ah和净 Ah
- 终端电压、最高/最低温度
- SEI、析锂、死锂、正负极LAM
- 关键正负极孔隙率和活性材料体积分数
- 终止事件、事件时间、事件值及终止分类

### 7.2 RPT 与时序

`rpt_summary.csv` 记录局部容量差、两种SOH、诊断分支时间、主状态前后证据、是否更新 `Q_ref` 及派生目标。cycle-0相对初始容量SOH记为100%。

完整时序仅保存第1、25、75、175、350个aging cycle以及全部容量RPT。代表循环时序必须包含整个循环的各阶段，不能只保存最后一个UDDS解段。

### 7.3 图形

生成：

- 模拟容量/SOH与未经拟合的W10实测容量叠加图
- 温度随循环变化图
- SEI、析锂、死锂和LAM贡献图
- 代表循环电流、电压和温度时序图
- 仅当两种模式均为 `COMPLETED` 时生成virtual/strict-W10对比图

图形和输出写入失败属于输出损坏，归为 `NUMERICAL_FAILURE`。

3. 获取并持有运行目录全生命周期排他锁。
4. 运行配置及输入文件指纹计算。
5. 执行UDDS周期识别与波形验证。
6. 构建DFN、参数、网格及IDAKLU求解器。
7. 显式构造约20% SOC规范初态并记录状态指纹。
8. 验证必需输出变量在处理后的模型中存在。
9. 写出完整运行配置和环境元数据。

preflight 不执行老化仿真。

## 9. 测试和 smoke test

### 9.1 非求解测试

补齐原设计列出的单元测试和 FakeBackend 状态机测试，包括RPT节点调度、批内 `Q_ref` 冻结、恢复指纹拒绝、事务一致性、cycle-350行为和三种终态。

### 9.2 真实 PyBaMM 短求解 smoke test

增加显式 `--smoke` 入口，仅执行：

1. 一个短恒流容量终止事件，验证自定义容量事件与电压事件分类。
2. 一个缩短目标的实际UDDS段，验证drive-cycle控制和净容量事件。
3. 保存checkpoint、重新加载并从该状态继续一个短段。
4. 在 checkpoint 后写入模拟的未提交 CSV、JSONL、时序和图形输出，恢复时验证自动回滚、审计归档及幂等性。
5. 比较连续路径与恢复路径的最终时间、容量及状态向量。
6. 在隔离诊断分支上执行短virtual诊断并验证主状态不变。
7. 启动两个进程竞争同一 smoke 运行目录，验证全生命周期单写者锁。

smoke test 使用独立输出目录和显著缩短的容量目标，不计入正式老化结果，也不修改正式运行目录。

### 9.3 正式运行门槛

只有以下条件全部满足后，代码才标记为正式运行就绪：

- 全部非求解测试通过
- W10文件集成测试通过
- DFN构建和必需变量检查通过
- 真实PyBaMM smoke test通过
- checkpoint连续/恢复对比通过
- checkpoint后未提交输出的自动回滚、前缀损坏拒绝和幂等恢复测试通过
- 显式20% SOC规范初态及virtual cycle-0 RPT状态指纹检查通过
- 运行目录全生命周期单写者锁并发测试通过
- 未发生未分类异常

整改任务完成时只给出350-cycle正式运行命令，不自动执行该命令。

## 10. 交付范围

本次整改修改现有模块，不复制两套模式实现。预计涉及：

- `config.py`：preflight、显式20% SOC规范初态、周期识别、恢复和smoke配置
- `udds.py`：全段周期识别、相位平均和解析截断
- `backend.py`：分支、阶段结果、事件分类和状态恢复
- `diagnostics.py`：virtual/strict RPT证据与时间语义
- `protocol.py`：显式阶段和容量误差检查
- `runner.py`：事务、checkpoint恢复、正确的 `Q_ref` 顺序和终态
- `output.py`：原子写入、完整字段、事务清单、全生命周期单写者锁和未提交输出回滚
- `figures.py`：实测容量叠加及双模式比较
- `cli.py`：`--resume`、`--smoke` 和解释器检查
- `tests/`：原设计要求及本整改新增测试

不修改 `OKane2022` 老化参数，不拟合W10容量数据，不实现HPPC/EIS物理过程，不启动350-cycle正式仿真。
